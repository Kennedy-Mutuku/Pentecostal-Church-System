# CU Finance Management System — Project Overview

## What We're Building

A web-based finance management system for the KSU Christian Union (CU) that replaces manual record-keeping with a digital platform. The system tracks all money coming in (offerings, tithe, thanksgiving, AOB) and going out, whether received via M-Pesa or cash. It maintains a requisition book, a ledger of all incomes and expenses, and an asset register for CU property. Financial statements can be generated by date range, and an audit trail logs every action for full transparency and accountability.

---

## System User Roles

The system enforces separation of duties through 7 distinct roles. Each user is assigned one role and can only access what their role permits.

| Role | Purpose | What They Can Do |
|------|---------|-----------------|
| **System Admin** | System management | Create/manage user accounts, reset passwords, view audit logs, delete or correct records, handle error corrections |
| **Treasurer** | Day-to-day financial operations | Record cash in/out with receipts, manage the requisition book (request amount, voucher, amount spent), maintain the ledger (incomes & expenses by category), record asset valuations, generate financial statements |
| **Auditor** | Oversight (read-only) | Review all financial records and treasurer's reports to ensure transparency and accountability |
| **Chair Accounts** | Financial reporting & asset monitoring | Prepare financial statements, view treasurer's reports, monitor condition and status of CU assets |
| **Chairperson CU** | Authorization & decision-making | Authorize cash deposits and withdrawals from the treasurer, view financial reports, generate statements by selected date range |
| **Patron** | Final approval authority | Approve financial decisions, provide soft approval for transactions covering withdrawals, deposits, administration, activities, news, students, and statements |
| **Member** | View own records | View personal contributions (phone number, amount, category) |

### Chair Accounts vs Chairperson CU

- **Chair Accounts** is the accounting officer — they **prepare** financial statements and **monitor** assets. Think of them as the bookkeeper.
- **Chairperson CU** is the overall CU leader — they **authorize** money movement (deposits/withdrawals). They are the decision-maker, not the bookkeeper.

## Core Modules

### 1. Cash Management
- **Cash In:** Record incoming money by category (offering, tithe, thanksgiving, AOB) and source (M-Pesa or cash)
- **Cash Out:** Record outgoing money with descriptions
- **Receipts:** Upload receipt images for every transaction
- **Balance:** View current balance (total in minus total out)
- **Approval:** Chairperson and Patron authorize deposits and withdrawals

### 2. Requisition Book
- Treasurer creates a requisition with the exact amount requested and reason
- Chairperson or Patron approves or rejects the requisition
- Once approved and spent, the treasurer completes the requisition by recording the exact amount spent and attaching a voucher
- Status flow: **Pending -> Approved -> Completed** (or **Rejected**)

### 3. Ledger
- Tracks all expenses and incomes
- Cash-in categories: offerings, tithe, thanksgiving, AOB
- Cash sources: M-Pesa, cash
- Filterable by type, category, and date range

### 4. Asset Management
- Register CU assets with name, description, and valuation
- Track asset condition: good, fair, or poor
- Chair Accounts monitors asset status

### 5. Reports & Statements
- Generate financial statements filtered by date range
- Income vs expense breakdown
- Category breakdown (how much came from offerings vs tithe vs thanksgiving vs AOB)
- Balance reports

### 6. Audit Trail
- Every action in the system is logged: who did what, to which record, and when
- Visible only to the System Admin
- Actions tracked: create, update, delete, approve, reject, password reset

## Tech Stack

| Layer | Technology | Purpose |
|-------|-----------|---------|
| Backend | Node.js + Express.js | REST API server |
| Database | MongoDB + Mongoose ODM | Data storage and modeling |
| Authentication | JWT + bcrypt | Secure login and role-based access |
| File Uploads | Multer | Receipt and voucher uploads |
| Frontend | React.js (Vite) | User interface |
| Payment | M-Pesa Daraja API | Mobile money integration |
| Containerization | Docker + Docker Compose | Consistent dev environment |

## Project Phases

Development is split into 5 phases. Each phase, teams rotate between backend, frontend, and integration work so everyone gains full-stack experience.

### Phase 1: Foundation & Authentication
> Get the project running and users logging in

| Task | Description | Team |
|------|------------|------|
| Auth UI | Login page, admin registration form, password reset, JWT handling, protected routes | Team 1 |
| Backend fixes | Input validation, file upload security, user update endpoint | Team 2 |
| Frontend setup + Testing | React Router, shared layout/navigation, global auth context, API service layer + test Teams 1 & 2 deliverables | Team 3 |

**Deliverable:** Admin can log in, register other users, and reset passwords.

### Phase 2: Cash Management (Ledger)
> Core financial operations — cash in and cash out

| Task | Description | Team |
|------|------------|------|
| Transaction forms UI | Cash-in/out forms with category, source, phone, amount, receipt upload | Team 2 |
| Transaction views | Filterable transaction list, detail page, balance summary | Team 3 |
| Backend enhancements | Transaction approval endpoints, pagination on all lists, requisition filters | Team 1 |

**Deliverable:** Treasurer records cash in/out. Chairperson/Patron approve. Transactions are viewable and filterable.

### Phase 3: Requisitions & Assets
> Complete the requisition workflow and asset tracking

| Task | Description | Team |
|------|------------|------|
| Requisition UI | Create/view requisitions, approve/reject buttons, complete with voucher upload | Team 3 |
| Asset Management UI | Add/edit/delete assets, asset list with condition indicators | Team 1 |
| Backend gaps | Member contributions endpoint, single requisition GET, requisition status/date filters | Team 2 |

**Deliverable:** Full requisition lifecycle. Assets managed. Members see own contributions.

### Phase 4: Reports & Dashboards
> Financial statements, charts, and role-based dashboards

| Task | Description | Team |
|------|------------|------|
| Financial statements UI | Statement view with date picker, income/expense breakdown, category breakdown | Team 1 |
| Role dashboards | Admin, Treasurer, Chairperson, and Member landing pages with relevant summaries | Team 2 |
| Audit logs & charts | Audit log table, bar/pie charts for category breakdowns, balance trends | Team 3 |

**Deliverable:** Every role sees a relevant dashboard. Statements generated by date. Audit trail visible.

### Phase 5: Polish, Security & M-Pesa
> Production readiness

| Task | Description | Team |
|------|------------|------|
| Security & error handling | Rate limiting, error pages, file restrictions, soft delete, session timeout | Team 1 |
| Responsive design & UX | Mobile layouts, loading states, notifications, form errors, confirmation modals | Team 2 |
| M-Pesa integration | STK push, payment confirmation callback, link payments to transactions | Team 3 |

**Deliverable:** Production-ready system with M-Pesa, secure and mobile-friendly.

### Team Rotation Summary

## Git Workflow

1. **Never push directly to `main`** — always create a branch first
2. Create a feature branch: `git checkout -b feature/your-feature-name`
3. Make changes, commit with a clear message
4. Push your branch: `git push -u origin feature/your-feature-name`
5. Open a Pull Request targeting `main`
6. Wait for your team lead to review and merge

### Branch Naming

| Type | Format | Example |
|------|--------|---------|
| Feature | `feature/short-description` | `feature/login-page` |
| Bug fix | `fix/short-description` | `fix/cash-in-validation` |
| Docs | `docs/short-description` | `docs/api-endpoints` |

## API Endpoints

Full list of backend endpoints. See `docs/requirements.md` for detailed role access per endpoint.

| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/api/auth/login` | User login (public) |
| POST | `/api/auth/register` | Register new user (admin only) |
| POST | `/api/auth/reset-password` | Reset user password (admin only) |
| GET | `/api/users` | List all users (admin only) |
| GET | `/api/users/:id` | Get single user (admin only) |
| DELETE | `/api/users/:id` | Delete user (admin only) |
| POST | `/api/transactions` | Record transaction (treasurer) |
| GET | `/api/transactions` | List transactions (multiple roles) |
| GET | `/api/transactions/balance` | Get balance summary (multiple roles) |
| GET | `/api/transactions/:id` | Get single transaction (multiple roles) |
| POST | `/api/requisitions` | Create requisition (treasurer) |
| GET | `/api/requisitions` | List requisitions (multiple roles) |
| PUT | `/api/requisitions/:id/approve` | Approve requisition (chairperson/patron) |
| PUT | `/api/requisitions/:id/reject` | Reject requisition (chairperson/patron) |
| PUT | `/api/requisitions/:id/complete` | Complete requisition (treasurer) |
| POST | `/api/assets` | Add asset (treasurer) |
| GET | `/api/assets` | List assets (multiple roles) |
| GET | `/api/assets/:id` | Get single asset (multiple roles) |
| PUT | `/api/assets/:id` | Update asset (treasurer) |
| DELETE | `/api/assets/:id` | Delete asset (admin only) |
| GET | `/api/reports/statement` | Financial statement (multiple roles) |
| GET | `/api/reports/categories` | Category breakdown (multiple roles) |
| GET | `/api/audit-logs` | View audit logs (admin only) |
